# InnoDB 페이지 크기 실험 (8KB · 16KB · 32KB)

## 1. 목적과 가설

- **목적**: InnoDB 페이지(블록) 크기를 기본값 16KB에서 바꿀지 측정으로 정한다.
- **가설**: "우리 서비스는 조회 전용이고 경기·선수 단위 범위 조회/집계가 많으니 페이지를 키우면(32KB) 빨라질 수 있다."
- 결과가 어떻든 측정값 그대로 결론을 낸다. 차이가 없으면 16KB를 유지한다.

## 2. 환경

| 항목 | 값 |
| --- | --- |
| 기기 | Apple M4 Pro, macOS 15.7.9, Docker Engine 29.1.3 (Docker VM: 14 CPU, 메모리 7.65GiB) |

| 테이블 | player_set | ban | team_set | match_set | lck_match | champion | player | player_season | team | stage |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

- buffer pool 시작 시 자동 로드는 끄고 비교했다. 켜 두면 재시작해도 이전 페이지가 메모리에 다시 올라와 콜드 측정이 되지 않는다.
- 기존 로컬 DB와 배포 서버는 바꾸지 않았다. 16KB 컨테이너는 3307 포트를 다른 컨테이너가 쓰고 있어 3310으로 열었다 (측정은 `docker exec`로 해서 포트와 무관).

## 3. 방법

스크립트: [scripts/page-size-experiment/](../scripts/page-size-experiment/) (`run.sh` 하나로 생성 → 적재 → 측정 → 표 → 삭제)

1. **쿼리 5개**: 서버를 16KB 컨테이너에 붙여 API를 호출하고 MySQL general log에서 실제 실행된 SQL을 그대로 가져왔다. 파라미터는 실데이터 값이다.

   | 쿼리 | API | 고정 파라미터 | 결과 행 |
   | --- | --- | --- | ---: |
   | 경기 목록 | `GET /api/v1/matches` | 2026-04-20 ~ 04-26 | 10 |
   | 세트 상세 (스코어보드) | `GET /api/v1/matches/19417/sets/3` | set_id 23083 | 10 |
   | 순위표 계산 | `GET /api/v1/standings` | 전체 경기의 팀별 세트 승수 | 296 |
   | 선수 랭킹 (시즌 세트 평점) | `GET /api/v1/players?position=MID` | 2026 시즌 전체 세트 | 3,770 |
   | 선수 경기 기록 | `GET /api/v1/players/16507/games` | Faker | 86 |

2. **콜드**: 쿼리마다 컨테이너 재시작 + Docker VM의 OS 페이지 캐시 비우기(`drop_caches`) → `EXPLAIN ANALYZE` 1회.
3. **웜**: 콜드 직후 같은 쿼리를 `EXPLAIN ANALYZE`로 20회 → 평균·최소·최대. 시간은 최상위 노드의 `actual time`(마지막 행까지, ms)이다.
4. **반복**: 1~3을 같은 조건으로 3회 돌려 반복 간 편차를 봤다. 표 1·4의 평균·최소·최대는 1회차 값이고, 반복 값은 차이가 오차 범위인지 판단하는 데 쓴다.
5. **저장 공간**: `ANALYZE TABLE` 후 `information_schema.TABLES`(DATA_LENGTH, INDEX_LENGTH)와 `mysql.innodb_index_stats`(실제 리프 페이지 수 `n_leaf_pages`).
6. **디스크 읽기 비율**: 측정 전후 `Innodb_buffer_pool_reads ÷ Innodb_buffer_pool_read_requests`.
7. **buffer pool 최소 시나리오**: 같은 측정을 buffer pool을 줄여 다시 했다. 요청은 5MB였지만 32KB 페이지는 최소 8,519,680바이트가 필요해 5MB로는 MySQL이 시작하지 않는다
   (`Buffer pool size is too small, must be at least 8519680 bytes`). 세 곳을 같은 값으로 두기 위해 **9MB**로 했다.

## 4. 결과

### 표 1. 쿼리별 웜 평균 시간 (buffer pool 128MB, 20회 평균, 최소~최대, ms)

| 경기 목록 | 0.039 (0.034~0.055) | 0.038 (0.035~0.049) | 0.038 (0.034~0.050) | 0.039~0.043 / 0.037~0.039 / 0.038~0.046 |
| 세트 상세 | 0.055 (0.050~0.073) | 0.080 (0.053~0.151) | 0.056 (0.048~0.075) | 0.055~0.060 / 0.057~0.080 / 0.056~0.057 |
| 순위표 계산 | 1.703 (1.500~1.880) | 1.639 (1.540~1.870) | 1.638 (1.540~1.800) | 1.673~1.776 / 1.622~1.723 / 1.638~1.750 |
| 선수 랭킹 | 2.490 (2.200~3.810) | 2.770 (2.260~4.890) | 2.430 (2.120~2.600) | 2.365~2.490 / 2.377~2.770 / 2.430~2.556 |
| 선수 경기 기록 | 1.152 (1.020~1.810) | 0.645 (0.556~0.841) | 0.653 (0.566~0.734) | 1.073~1.476 / 0.645~0.674 / 0.651~0.658 |

- 16KB와 32KB의 3회 평균 차이는 쿼리별로 −13.7% ~ +11.4%이고 방향이 쿼리마다, 회차마다 바뀐다.
  모든 쿼리에서 두 크기의 반복 범위가 겹친다. 차이가 가장 큰 세트 상세(−13.7%)는 16KB 1회차 한 번(0.080ms, 최대 0.151ms) 때문이고, 2·3회차는 16KB 0.057·0.058ms, 32KB 0.056·0.057ms로 같다.
- 8KB의 선수 경기 기록만 세 번 모두 약 1.1~1.5ms로 느렸다. 실행 계획을 비교하면 8KB에서는 재시작 직후 옵티마이저가
  `stage` 테이블을 먼저 전체 스캔해 해시 조인하는 계획을 골랐고(51회 실행해도 유지), 16KB·32KB는 `stage`를 기본 키로 찾는 계획이었다.
  같은 계획으로 실행될 때는 8KB 0.689ms, 16KB 0.675ms, 32KB 0.653ms로 같았다. 페이지 수가 옵티마이저 비용 계산에 들어가서 생긴 계획 차이이고, 디스크 읽기와는 관계없다 (웜 디스크 읽기 0회).

- **9MB로 줄여도 데이터(약 3MB)가 buffer pool 안에 다 들어갔다.** 웜 디스크 읽기는 128MB일 때와 같이 0~1회다.
  32KB는 빈 페이지가 0이 될 만큼 찼지만 읽기 비율은 그대로였다. "데이터가 메모리보다 클 때"는 지금 데이터 규모로는 만들 수 없었다 (32KB의 최소 buffer pool 8.1MB > 데이터 3MB).

- 8KB 1회차의 세트 상세·선수 랭킹·선수 경기 기록이 느린 것은 데이터를 넣은 직후 측정이라 실행 계획이 달랐기 때문이다.
  세트 상세는 `player_set` 전체 스캔 계획이었고(웜 읽기 요청 25,763회, 16KB는 1,460회), 선수 랭킹·선수 경기 기록도 읽기 요청 수가 16KB와 달랐다.
  2회차부터 세트 상세는 다른 크기와 같은 인덱스 계획으로 돌아왔다. 이 때도 웜 디스크 읽기는 0회라 I/O 때문은 아니다.

## 5. 결론: 16KB 유지

- **데이터 전체(데이터+인덱스 약 3MB)가 buffer pool(128MB)에 들어가는 규모라, 페이지 크기가 성능에 거의 영향이 없다.**
  웜 상태에서는 세 크기 모두 디스크 읽기가 0이고, 16KB와 32KB의 시간 차이는 같은 크기를 반복 측정할 때의 편차 안에 있다 (표 1).
- 32KB는 콜드 때 읽는 페이지 수가 줄었지만(표 2) 시간은 일관되게 줄지 않았다 (쿼리에 따라 빠르기도, 느리기도 했고 차이는 1.4ms 안쪽). 가설("32KB가 빨라질 수 있다")은 이 데이터에서 확인되지 않았다.
- buffer pool을 세 크기가 모두 시작할 수 있는 최솟값(9MB)까지 줄여도 데이터가 메모리에 다 들어가서 결과는 같았다 (표 4).
- 8KB에서 보인 느린 결과는 I/O가 아니라 옵티마이저가 다른 실행 계획을 골라서 생긴 것이다.
- 페이지 크기는 데이터 디렉터리를 처음 만들 때만 정할 수 있어서, 바꾸려면 DB를 새로 만들고 전체를 덤프·복원해야 한다. 이득이 측정되지 않았으므로 바꿀 이유가 없다.
- **다시 검토할 조건**: 데이터+인덱스가 buffer pool 크기에 가까워지거나 넘어서고, 평소 운영 중 `Innodb_buffer_pool_reads ÷ read_requests`가 눈에 띄게 오를 때 (지금은 약 3MB / 128MB, 웜 읽기 비율 0%).

### 한계

- 한 대의 Mac에서 Docker VM 안의 MySQL로 측정했다. 배포 서버(GCP e2-small)와 디스크·CPU가 다르다.
- `EXPLAIN ANALYZE`는 계측 비용이 포함된 시간이고, 쿼리가 수 ms 이하라 작은 흔들림도 비율로는 크게 보인다.
- 콜드 측정은 쿼리당 1회(반복 3회)라 값이 흔들린다.
